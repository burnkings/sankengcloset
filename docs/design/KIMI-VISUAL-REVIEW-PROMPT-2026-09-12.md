## §2 提示词（复制这段给 Kimi）

````
# 角色

你是资深移动端产品设计师。这次不用你读代码猜——我给你真机截图，
请你基于**实际渲染效果**做视觉评审。你的价值在于"看出界面哪里不对"，而不是"分析代码结构"。

# 项目

三坑绮橱（JK / Lolita / 汉服 的兴趣消费 App），uni-app x，Android 内测 Beta。
主链路：内容 Feed → 发现搜索 → 收藏追踪 → 购买外跳 → 订单导入与尾款提醒 → 入橱。

# 设计定位（先记住，否则会评偏）

1. **现代化 App 是主语，三坑只是形容词。** 目标是"一个做得很好的现代内容消费 App，恰好服务三坑人群"。
   它与小红书、得物、B站会员购这类现代 App 的差距应**基本为零**。
2. 参考小红书 / WorkBuddy 只学**样式与布局**（视觉语言），不涉及业务逻辑与信息架构。
3. 三坑只影响 6 个口味参数：底色冷暖（暖白 #FAF8F7）/ 圆角档位（柔一档）/
   强调色相（玫粉 #D45F7E，**只换色相不换克制程度**）/ 图片权重 /
   时间状态优先级（发售·预售·尾款·截团）/ 文案语气。其余全部服从现代通用标准。
4. 信息密度分两档：内容浏览页（首页/发现/详情/专题）图片主导、信息从轻、留白大；
   管理决策页（购买/提醒/衣橱/预算）紧凑可扫、状态与金额强语义。

# 截图

docs/design/screenshots/2026-09-12/ 下，文件名 = 页面-主题-状态。
看不清细节的图直接说"这张看不清，请重截"，**不要猜**。

# 我要你做什么（严格按四步）

**第一步 · 逐张"看图说话"。** 每张图先回答三个问题：
  a) 第一眼落在哪里？——视觉焦点是否落在"这一屏最该被看到的东西"上
  b) 有没有"说不上哪里怪"的地方？——这类直觉最值钱，一定要说出来，哪怕你说不清原理
  c) 把它和小红书 / 得物放在一起，差在哪？——具体差在哪个元素、哪个间距、哪个层级

**第二步 · 分级。** P0 = 肉眼可见的粗糙或错误（不用解释就能看出不对）；
P1 = 不一致（同类元素在这页和那页长得不一样）；P2 = 可以更好（审美提升空间）。

**第三步 · 每条给可执行方案。**
  文件:行号 | 改前 | 改后 | 理由
  拿不到行号就给"组件名 + 具体 token"（radius / spacing / 字号字重 / 颜色 / 状态）。
  **禁止**只说"建议加大留白""层级可以更清晰"——必须落到具体数值。

**第四步 · 区分"确定要改"和"需要我拍板"。**
  审美取舍类（双列要不要更宽、卡片信息区要不要加一行、某处留白要不要收）
  单独列出来让我选，**不要替我决定**。

# 明令禁止

- 不要重写设计系统：只能对现有 token 做增量补充，且必须说明兼容影响。
- 不要推翻信息架构、不要建议新增页面/路由/功能。
- 不要用装饰制造"三坑感"：禁止粉色铺底与渐变、蕾丝/蝴蝶结/贴纸、插画风空态、
  花体艺术字、彩色投影。三坑身份靠参数和信息优先级体现，不靠装饰。
- 不要用"建议优化"这类空话凑数。**宁可只报 3 条真问题，不要列 20 条凑数。**

# 技术红线（给方案时必须遵守，否则方案无法落地）

- 样式只能写在 script 的 UTSJSONObject 里、用 `:style` 绑定；单位只能 rpx；不使用 `<style>` + class。
- 不支持：伪类、CSS 变量、backdrop-filter / 玻璃拟态；linear-gradient 支持受限，需先验证。
- 主题色必须 `computed` 返回 `n.value.*`（写成模块级常量会导致深色模式不刷新）。
- 按压态用 `@touchstart` / `@touchend` 切响应式状态，不能写 CSS 伪类。
- 可点元素热区 ≥ 88rpx；正文对比度 ≥ 4.5:1。
- 横向 `scroll-view` 必须带 `:show-scrollbar="false"`（内容放得下时优先不用滚动容器）。

# 本轮已修（这些不用再报，除非你发现新问题）

- 骨架屏列距对齐真实 Feed（原先加载完会"缩缝"）
- 首页违规 `<style>` 块移除；首页错误行、收藏页提醒按钮补 88rpx 热区
- 购买页订单卡**接回金额行**（此前样式写了但模板没渲染，卡片上根本没有金额）
- 15 处 `brand.primary` 模块级固化 → `n.value.iconActive`（深色自适应）
- 发现页补首屏骨架 / 失败重试 / 空提示三态
- 预算页分类圆点 8 个硬编码色 → 浅深双表；进度条预警色归入 `semantic.warning`
- 提醒页「已过期」从最弱的灰色 → `semantic.error` 强语义

# 输出格式

1. 逐张截图的评审（按第一步的三个问题）
2. P0 / P1 / P2 问题表
3. 每条问题的可执行方案（含行号或组件 + 具体数值）
4. 需要我拍板的取舍清单

现在开始：先看图，把"看得见的问题"讲透。
````

## §3 使用建议

- **一次给全，不要分批问。** 把 8–12 张图 + 上面这段提示词一次性发过去，让它出一份完整评审。来回问答最费积分。
- **先只让它评审，不要让它改代码。** 拿到评审后你自己筛一遍（它可能有你不认同的审美判断），确认了再让它改，或者让我改——**改代码这块我更熟项目红线，也更省**。
- **如果它的评审里 P0 很少**，说明方向没问题，可以直接进入"需要我拍板的取舍清单"那部分做决策。
- **深色那几张重点看**：本轮改了 15 处强调色和预算分类色，但源码检查查不出"深色下好不好看"，只有截图能验。
