## 答你问的（不改代码的部分）

### 4「失败插画」选哪个
**选 B：深色下换中性（`n.value.textDisabled` 三档透明度），不保留粉。**
理由：
1. 失败态的第一诉求是"安静 + 可重试"，不是"好看"。亮粉插画在暖黑底上会成为全页最亮的东西，把注意力从「重试」按钮上抢走。
2. 粉 = 品牌正向色。用品牌色渲染"失败了"这件事，语义上自相矛盾（红/粉在多数人心里已经是警示色，和"点击重试"叠在一起会让人以为出错了两次）。
3. A 方案（深色下用低透明度粉）能减小落差，但仍然是"彩色插画"；失败的占位应该退到背景层。
4. 只影响加载失败这一刻，改成中性不损失任何信息（文案「三坑绮橱 · 点击重试」照旧）。

### 9「屏蔽品牌」更适合的位置
现在是品牌行里紧挨品牌名的粉色小胶囊。问题：**低频 + 负向操作占了主信息行**。
建议（推荐 D）：

### 10 旋裙是汉服的分类吗
是，但**不是我们 App 的分类**。「旋裙」是**宋代**的一种女裙形制（前后两片交叠、行走时旋转摆动，故称旋裙），
属于汉服**下裙**体系，常与"宋裤"并称，一般归在"宋制"名下。
在我们 App 的字段体系里：坑向只有 JK / Lolita / 汉服 / 其他；「宋制」这种形制信息应该走 `subCategory`（子分类）或商品标题，
**不要**强行塞进坑向枚举。当前假数据里它是商品名的一部分，是对的。

### 11 同时有 JSK、OP 会不会并列展示标签
**当前不会**。商品详情的 `subCategory` 是**单值**字段，只渲染一枚 `subChip`。

UI 上最多显示 `JSK 等 2 件`，**不要并列刷多枚同权重标签**（会和不分主次的卖点标签打架）。

### 12 规格里加尺码

真实商品带 variants 时会自动显示。要我在 mock 里补一组示例尺码也可以（会写进 mock 数据，不动领域模型）。

### 13 搭配度算法是什么
`services/ai/wardrobe-compatibility-service.uts`，明确是**规则计算，不冒充视觉模型**（代码注释里就这么写的）：
- 衣橱为空 → 返回 `-1`，**不展示分数**
- 把商品标题+副标题+角标拼成文本，在**颜色词表**（黑/白/红/粉/蓝/绿/棕/米/紫/灰/黄/金/银）和**风格词表**（甜/哥特/古典/学院/森/优雅/华丽/日常/洛丽塔/中式/明制/宋制/旗袍）里各命中一个
- 逐件比对衣橱单品：**同坑向** +1（每件）、文本命中同色 → `colorMatches`、命中同风格 → `styleMatches`
- 算分：`min(同坑向件数,3)×12 + (有色系?24:0) + (有风格?24:0) + min(16, 衣橱件数×2)`，上限 100
- 文案：「基于衣橱中的 N 件同坑向、N 件同色系、N 件同风格计算」；标签不足时给"暂按坑向和单品数量计算"

一句话：**坑向是最强信号（每件 12 分、封顶 36），色系/风格各 24 分的门槛分，衣橱体量最多给 16 分**。
注意 `matchedItems` 只取前 3 件，所以「可优先试搭」最多列 3 个名字。

## 答 7 / 8 / 9（见对话正文）

### 7 JSK / OP 同时卖 —— 处理模型
**关键判断：对 Lolita 来说"型别"不是分类标签，而是"规格"（SKU 属性）**，和颜色、尺码同级。
- 一个链接卖 JSK + OP → 它们是**可选项**，所以并列展示 chip 是**正确的**，不算"重复标签"。
- 落地方式（本批已实现）：`ProductVariant.styleName` → 详情页「可选型别」行；**列表卡上不出现型别**（避免多值标签刷屏）。
- 衣橱侧保持"单值"（一件衣服只有一个型别）→ `ChipPicker` 单选不变。两边语义不同，不要强行统一。
- 后端约定：`product_variants.style_name`（缺省空串）；若某商品只有单一型别，就只出 1 枚 chip。

### 8 搭配度算法：能落地吗
**结论：目前这版是"可解释的启发式 v1"，不是意淫，但也撑不起一个百分比分数 —— 按现状上线会失分。**
具体问题（`services/ai/wardrobe-compatibility-service.uts`）：
1. **送分**：`coverageScore = min(16, 衣橱件数×2)` —— 只要衣橱有货就白拿分，8 件即满分。分数与"般配"无关。
2. **粗粒度**：色系/风格各是"有→24 分"的**布尔**，命中 1 件和 10 件同分。
3. **纯关键词匹配**：在标题+副标题+角标里找颜色词/风格词；"雾霾蓝"、"若草色"这类词表外颜色直接漏检；靠词表覆盖，不靠理解。
4. **不会看**：完全不用图片。而 Lolita 搭配的判定核心恰恰是**图案/柄柄/腰线**这些视觉特征 —— 这部分它一点没做。
5. **词表窄**：颜色 13 个、风格 13 个，且风格词表里"洛丽塔/明制/宋制"混着坑向概念，语义不齐。

市面上有没有公开可用的稳定算法？
- **没有"开箱即用 + 免费 + 稳定"的搭配度 API**。淘宝/得物的搭配推荐是内部能力，不对外。
- 学术/开源路线是有的，但都需要**训练数据**：Outfit Compatibility（Polyvore-U / Polyvore-Outfits 数据集）做"这套搭不搭"的成对打分；用 CLIP/SigLIP 做图-文/图-图相似度；工业界常用**共购/同店搭配**统计 + 图像相似做召回。
- 关键缺口：我们没有"搭配标注"数据，也没接入商品图的向量化能力 —— 所以**现在做真算法缺料**。

**我的建议（三选一，倾向 B）**：
- **A 先下线**：把"搭配度 %"和进度条拿掉，换成基于现有规则的低承诺文案「衣橱里有 N 件同坑向、N 件同色系单品」（不冒充分数）。改动最小、零风险。
- **B（推荐）保留入口但降级 + 修分**：① 去掉 `coverageScore` 送分；② 色系/风格改按件数计分（如 `min(件数,3)×8`）；③ 文案改成"参考"而非"搭配度"；④ 明确标注"基于标签的估算"。
- **C 先不做**：等有了商品图向量 + 搭配语料再做真算法（这需要后端一起排期）。

### 9 "主题 token"是什么
**设计令牌（design token）= 给"设计决策"起的变量名**。比如不写 `#D45F7E`，而是写 `brand[500]`；不写 `16rpx`，而是写 `radius.md`。
我们仓库里在 `theme/tokens/` 下：`colors.uts`（颜色）、`typography.uts`（字号/字重/行高）、`spacing`、`radius`、`z-index.uts`（层级）、`responsive`（间距/卡宽）。

**本项目最关键的一条规矩**：token 分两类 ——
| 类型 | 例子 | 深色模式行为 |
|---|---|---|
| **静态 token** | `brand[500]` = `#D45F7E` | ❌ 不刷新。深色下还是这个死值 |
| **主题响应 token** | `n.value.iconActive` | ✅ 浅 `#D45F7E` / 深 `#E47A96` 自动切换 |

所以"改成主题 token"= 把 `brand[500]` 这种**模块级常量**换成 `computed` 里的 **`n.value.*`**。
技术原因：`n` 是 `reactive`（`theme/use-theme.uts` 里的 `_state`），写在 `computed` 里才会被 Vue 追踪、主题一变就重算；
写成模块级 `const xx = { color: brand[500] }` 拿的是快照，永远不会变。源码门禁 `scripts/check-source-gates.js` 第 2 条就在拦这个（`const xx = { color: n.value.xxx }` 直接判失败）。

## 3. 已过期圈的 A / B，我推荐 **A（保留红描边空心圈）**
| | 做法 |
|---|---|
| A（推荐） | 空心 + `semantic.error` 红描边，不填充、不画勾 |
| B | 中性灰描边，只留右侧「已过期」红字 |

推荐 A 的理由：
1. 「已过期」是需要被**扫到**的异常态；B 会让它在"待提醒"堆里完全隐形，只能逐行读右侧文字才能分辨，扫读效率明显下降
2. A 只是 **2rpx 细描边、不填充**，视觉重量远低于"红底"，不会喧宾夺主
3. 与「已完成」实底绿 + 勾区分明确：细红圈 = 逾期未完成，实底绿勾 = 已完成
4. 红圈同时是"该处理了"的行为提示 —— 点它就完成，路径一致

**什么时候该改选 B**：如果你的"已过期"分组经常一屏十几条，满屏细红圈会变噪点，那时 B 更稳。
