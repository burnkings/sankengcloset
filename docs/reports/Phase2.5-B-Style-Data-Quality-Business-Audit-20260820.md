## 1. Executive Summary

- Style 数据**基本可信**：120 个聚类抽样，正确聚合率 90.0%（108/120）
- 发现 3 个错误合并（2.5%，均为小物/配件混入多商品簇）——影响 3 个 Style、5 个商品
- 发现 2 个系统性问题：**品牌名变体假拆分**（甜嗑系 7 个店名 → 甜心萌兔被拆 5 个 style）+ **58.6% 商品未归类**
- 覆盖率 41.4% 在"宁缺勿错"原则下健康；A 类规则扩展可提升至约 57%
- Product→Release 链路**完全断裂**（product_releases 0 行）——这是当前最大的产品链路缺口，但不是 Style 数据问题
- 用户核心链路「看商品→看款式→看同款→回商品购买」**前段通畅**；「历史发售」断在数据层（代码已就绪）
- 结论：**PASS**。数据质量问题均为可治理项（WARNING），不构成架构/业务链路阻塞

### 3.1 错误合并案例（3 个，已复核属实）

| 款式 | 品牌 | 问题 |
|---|---|---|
| 小偶像 | 芒栗狸JK原创馆 | 打歌服套装 + 小礼帽（配件）混入 |
| 猫薄荷 | 芒栗狸JK原创馆 | 3 水手服套装 + 猫猫领结（配件）混入 |
| 小蛋糕 | 久久原创设计 | 花嫁伞（配件）+ 吊带连衣裙混入 |

根因：提取规则只按【款式名】聚类，未校验簇内商品品类一致性。**建议后续治理：多商品簇内 sub_category 差异过大（如服装 vs 配件）时拆分**。影响面小（3 style / 5 商品），不需要回滚 1180 行数据。

### 3.2 漏合并案例（系统性问题，已复核属实）

1. **Alice girl 十字姬**：5 个商品（2 连衣裙 + 3 小物）全部 style_id=NULL——裸款式名（无【】标记）未被提取，属于已知的规则边界
2. **甜嗑系品牌变体假拆分**：甜嗑 JK / 甜嗑设计室 / 甜嗑jk原创 / 甜嗑JK原创社 / 甜嗑工作室 / 甜嗑jk工作室 / 甜嗑原创设计 = **7 个品牌名变体** → 「甜心萌兔」被假拆为 5 个 style（11 个商品分散）；星桃/喵雪吟/喵可可/小野/岚音/曲奇浪花 同类问题。根因：数据源（淘宝店名注册变体）+ 严格 brand_id 聚类策略
3. **玻璃纸之夜蓟草之冠**：配件（皇冠胸针）独立成 style，未与同系列主体合并——边界可接受

## 5. Product → Style → Release 完整性

```
Brand ✅ → Style ✅ → Product ✅ → ProductRelease ❌
```

| 环节 | 状态 | 说明 |
|---|---|---|
| Style→Product | ✅ | 1391 商品绑定 1180 style，平均 1.18 商品/Style，0 orphan |
| 同款多色/多 listing | ✅ | 通过多个 Product 挂在同一 Style 表达（草莓咚咚 8、雪月铃 6 多色） |
| 再贩归属 | ⚠️ | 再贩商品作为独立 Product 存在，可挂同 Style，但**无法从数据区分首贩/再贩** |
| Product→Release | ❌ | product_releases 0 行，**完全断链**。详情页"发售信息"恒隐藏；蜜糖甜塔 5 个"定金/尾款/意向金"链接无法标注发售阶段 |

结论：链路断在 **Release 数据层**，代码侧已就绪（getStyle 关联商品、detail.uvue 发售信息模块 v-if="release !== null"）。填补 product_releases 是后续数据工程任务，与 Style 无关。

## 6. Search → Style → Product 链路

| 检查项 | 结果 |
|---|---|
| 搜索 SQL 是否 join styles | ✅ `LEFT JOIN styles st ON st.id = p.style_id` + `st.canonical_name ILIKE` |
| 搜索款式名（十字姬） | ⚠️ 商品标题命中可出商品；**不返回 Style 实体**（结果仍是商品列表） |
| aliases style 类型 | ❌ STYLE_ALIAS_TERMS 空数组、aliases 表 31 条全 category 型 |
| 重复结果 | ⚠️ 同一 Style 的多商品分别命中时可能连排（feed_score 全 0 时排序退化） |
| 搜到商品但搜不到 Style | ✅ 现状成立——"十字姬"5 个商品无 style_id，只能靠标题裸匹配 |

结论：Search→Style 链路**结构已接入（styles join + styleIds 分支 postgres.ts L421/448）**，缺的是数据（style 类型 alias + 款式名覆盖）。不做新搜索架构，等 Style Alias（NEXT）。

## 11. Phase 2.5-C 是否必要

**建议：Phase 2.5-C（Search Style 接入）为 NEXT 而非 NOW——数据侧缺口（Style Alias 词库 + 款式名覆盖）未就绪，直接做搜索聚合收益有限。**

更优先的下一步是**数据治理**（见 §12），其产出（品牌归一、A 类格式扩展、小物拆分）会直接提升 Search/Discovery 的所有下游效果。若产品要求先验证"款式搜索"体验，可用最小成本做：Style Alias seed（10-20 词）+ search 返回 style 聚合实体（复用已接入的 styles join，无新架构）。
