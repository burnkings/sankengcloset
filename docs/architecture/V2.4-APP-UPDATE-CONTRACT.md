# 检查更新 — 客户端实现与后端契约

> 更新日期：2026-09-25（前端配置分层落地后复核）
> 结论一句话：**前后端链路都已通**。`GET /api/v1/app/version` 线上已实现并可用，
> 缺的只是**服务端把版本号与更新字段填全**（当前只回 `latestVersion`，且落后于客户端一个版本）。
> 下载地址已由**前端平台配置兜底**，所以后端不填 `updateUrl` 也不会卡住发版。

## 0. 线上实测

```bash
curl https://api.sankengcloset.icu/api/v1/app/version
# HTTP 200
# {"requestId":"req-yq","data":{"latestVersion":"V2.5.0-beta.2","hasUpdate":false,"updateUrl":"","releaseNote":""}}
```

读法：

| 现象 | 含义 |
|---|---|
| 200 + `latestVersion` | 接口存在，可用 ✅（此前"缺接口"的判断是错的） |
| `latestVersion = V2.5.0-beta.2` | 服务端停在 beta.2，而客户端 manifest 已是 2.5.0-beta.4 → 客户端本地比较正确判为「无更新」，不会误报 |
| 无 `latestVersionCode` / `minVersionCode` | 强制更新能力用不了（客户端已支持，等字段） |
| `updateUrl` 为空 | **不再直接提示"待配置"**：先落到前端平台配置；两者都空才提示「下载地址尚未配置」 |

**服务端待补**：`latestVersion`（每次发版同步）、`latestVersionCode`、`releaseNote`；
需要强制升级时再给 `minVersionCode`。`updateUrl` 可选（前端有兜底）。字段语义见 §2。

## 0.1 前后端职责分工（本次确定的配置方案）

| 归属 | 字段 / 能力 | 为什么这样分 |
|---|---|---|
| **后端**（版本事实，唯一来源） | `latestVersion`、`latestVersionCode`、`minVersionCode`、`releaseNote`、`publishedAt` | 版本只有一个事实来源；何时停止服务老版本属运营策略，客户端无权自行判定 |
| **前端**（分发与策略） | 下载地址兜底、平台差异、检查总开关、强制更新开关、连点单飞 | 下载地址跟分发渠道绑定（APK 直链 / 各商店 / App Store），后端不必也不该知道；开关放前端才能在不改后端的情况下灰度或回滚 |
| **前端**（判定权） | 是否提示更新的最终判定 | 不信服务端 `hasUpdate` 布尔：服务端算子写错或脏缓存都不会误报 |
| **后端**（无权） | ~~`hasUpdate`~~ | 接口仍可返回，客户端忽略 |

前端配置集中在 **`config/app-update.uts`**（唯一来源）：

| 配置项 | 默认 | 作用 |
|---|---|---|
| `UPDATE_ENABLED` | `true` | 关掉后不发请求、直接「已是最新」（接口故障期止血） |
| `UPDATE_FORCE_ENABLED` | `true` | 关掉后忽略 `minVersionCode`/`minVersion`，一律允许「稍后」（强制更新出问题时可一键回滚） |
| `UPDATE_URL_ANDROID` / `UPDATE_URL_IOS` / `UPDATE_URL_DEFAULT` | `''` | 服务端 `updateUrl` 为空时的平台兜底地址。**待填** |

## 1. 前端现状（已实现）

| 环节 | 位置 | 行为 |
|---|---|---|
| 入口 | `pages/about/index.uvue`「检查更新」行 | **小程序端整行隐藏**（`showCheckUpdate` + `#ifdef MP-WEIXIN`），协议行数随之 3→2 |
| 请求 | `services/user-data/app-update-service.uts` | `GET /api/v1/app/version`（`apiGet`，基址 `config/runtime.uts` → `https://api.sankengcloset.icu`） |
| 单飞 | 同文件 `_checkInFlight` | 连点「检查更新」复用同一次在途请求，不重复打后端 |
| 比较 | 同文件 `compareVersion()` | **本地比较**版本号，不信服务端 `hasUpdate` 布尔 |
| 地址 | `config/app-update.uts` → `resolveUpdateUrl()` | 服务端 `updateUrl` 优先 → 平台配置 → default；全空才算「未配置」 |
| 弹窗 | 同页 `AppDialog` | 有更新 → 「发现新版本 x.y.z」+ 更新说明 + 「立即更新 / 稍后」；强制更新时**隐藏「稍后」**；无地址时按钮文案为「我知道了」 |
| 打开 | `utils/share.uts` 的 `openExternalUrl()` | App 端 `openSchema` 唤起浏览器 / 淘宝；非 App 端复制链接 |

历次加固点（都是真实缺陷）：

1. **版本号两处漂移**：`config/app-version.uts` 还是 `V2.5.0-beta.2`，而 `manifest.json` 已经是 `2.5.0-beta.4` /
   `versionCode 25004`。漂移会让"当前版本"被算小 → 对已是最新的用户误报"发现新版本"。
   已对齐，并由 `tests/app-update.test.cjs` 强制校验（不一致时 `npm run verify` FAIL）。
2. **信服务端布尔**：原 `info.hasUpdate = data['hasUpdate'] == true`。改成用 `compareVersion(latest, APP_VERSION) > 0`
   本地判定，服务端算子写错或缓存脏数据都不会误报。
3. **失败与"已是最新"无法区分**：原实现请求失败也显示「当前已是最新版本」。
   现在 `AppVersionInfo.requestFailed` 单独标记，页面提示「检查更新失败，请检查网络后重试」。
4. **没有强制更新**：新增 `forceUpdate`（服务端 `minVersionCode` 数字比较优先，退化用 `minVersion` 字符串比较），
   强制更新时弹窗不提供「稍后」。
5. **下载地址无兜底**：服务端 `updateUrl` 为空时弹窗给出一个点不动的「立即更新」。
   现在按平台兜底，且无地址时按钮改文案 + 正文说明。
6. 版本比较此前不存在，现按语义实现：`2.5.0 > 2.5.0-beta.4`、`beta.10 > beta.4`、`V2.5.0 == 2.5.0`、`2.6 > 2.5.9`。

单元测试：`tests/app-update.test.cjs`（**14 条**，全绿），覆盖版本比较、本地判定、强制更新、失败标记、
平台归一、地址选择优先级、单飞、版本常量对齐。

## 2. 后端接口契约（接口已在，补齐字段即可）

`GET /api/v1/app/version` — 无需鉴权，允许 CDN / 强缓存 300s。

请求参数（可选，按平台分别返回不同包地址）：

| 参数 | 说明 |
|---|---|
| `platform` | `android` / `ios` / `mp-weixin`（缺省 `android`） |
| `channel` | `beta` / `release`（缺省 `release`；内测包按渠道返回） |
| `currentVersionCode` | 客户端版本号，服务端可据此直接给出 `hasUpdate`（客户端只作参考，仍以本地比较为准） |

响应（包在既有 `{ requestId, data }` 里，字段名与客户端 `AppVersionInfo` 一一对应）：

```json
{
  "requestId": "req_01H...",
  "data": {
    "latestVersion": "2.6.0",
    "latestVersionCode": 26000,
    "minVersionCode": 25000,
    "updateUrl": "https://dl.sankengcloset.icu/app/sankeng-2.6.0.apk",
    "releaseNote": "1. 修复通知页深色模式卡片配色\n2. 检查更新支持强制升级",
    "publishedAt": "2026-09-24T10:00:00+08:00",
    "channel": "release"
  }
}
```

字段语义与硬约束：

| 字段 | 类型 | 约束 |
|---|---|---|
| `latestVersion` | string | **必填**，与 `manifest.json` 的 `versionName` 同一套写法；为空时客户端视为"已是最新"（不误报） |
| `latestVersionCode` | number | 可选，用于日志与灰度分析 |
| `minVersionCode` | number | 可选。**低于它 = 强制更新**（客户端隐藏「稍后」）。只在"老版本真的不能用"时才写（如接口破坏性变更），否则会把人锁死在更新页 |
| `updateUrl` | string | App = APK 直链或下载页；小程序可留空（走平台审核更新） |
| `releaseNote` | string | 弹窗正文，纯文本，勿超 200 字 |
| `publishedAt` | string | 可选，ISO 8601 |
| `hasUpdate` | boolean | **不要依赖**：客户端已改为本地比较。服务端仍可返回，客户端忽略 |

缓存与灰度建议：`data` 里按 `channel` 区分 beta/release；`latestVersion` 必须与真实已发布的
`versionCode` 对得上，否则会出现"点了立即更新却下载到旧包"。

## 3. 各平台差异（重要）

**微信小程序：不需要"检查更新"。** 版本由微信托管，冷启动自动更新，无法自选版本。
**已按此实现**：`pages/about/index.uvue` 用 `showCheckUpdate` + `#ifdef MP-WEIXIN` 在小程序端整行隐藏
（协议行数 3→2，不留空位），避免"点了永远说已是最新"的假功能。

**Android（App）：当前只能跳下载，不能自动安装。** 现状 `openExternalUrl` 会唤起浏览器/复制链接。
要做应用内直接安装，需要满足三件事，缺一不可：

1. `nativeResources/android/AndroidManifest.xml` 加 `<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES" />`
   （**当前没有这条**，已核对）；
2. 一个 UTS 原生插件：`uni.downloadFile` 下载到私有目录 → 用 `FileProvider` 生成 `content://` URI →
   `Intent(ACTION_VIEW, type=application/vnd.android.package-archive)` 拉起安装器；
   Android 7+ 不允许直接传 `file://`，必须 FileProvider（本项目已有 `nativeResources/android/res/` 可放 `xml/provider_paths.xml`）；
3. 首次安装时引导用户开启「安装未知应用」权限（`Intent(ACTION_MANAGE_UNKNOWN_APP_SOURCES)`）。

**上架注意**：多数应用商店（华为/小米/OPPO/vivo/应用宝）要求"应用内更新"必须走**本商店的更新通道**，
自行下载 APK 安装可能被判定为违规；若走商店分发，`updateUrl` 填商店详情页更安全。

## 4. 发版 checklist

1. 改 `manifest.json` 的 `versionName` / `versionCode`；
2. 同步改 `config/app-version.uts` 的 `APP_VERSION` / `APP_VERSION_CODE`（`npm run verify` 会拦截不一致）；
3. 后端把新版写进 `/api/v1/app/version`（至少 `latestVersion`，建议含 `releaseNote`）；
4. 需要强制升级时，在接口里给 `minVersionCode`；
5. 下载地址：优先在接口里给 `updateUrl`；若走固定分发页，直接填一次
   `config/app-update.uts` 的 `UPDATE_URL_ANDROID` / `UPDATE_URL_IOS` 即可长期不用管。
