# 微信登录 — 前后端契约与实测结论

> 更新日期：2026-09-28
> 一句话结论：**代码侧已全部完成**（前端 + 后端接口都在，且是公开路由）。**疑似**卡在**两处微信公众平台配置**：
> ①**API IP 白名单**（路径：开发管理 → 开发设置 → **开发者 ID** → IP 白名单）里没有后端服务器的**出口公网 IP**（后端 → 微信这一跳）；
> ②**服务器域名 → request 合法域名**没加 `api.sankengcloset.icu`（小程序 → 后端这一跳）。见 §1 / §1.1。
> ⚠️ 注意 ① 是**待验证的假设**，不是已证结论：现有探针只能证明「**本机**出口 IP 不在名单内」，
> 证明不了后端服务器在不在（理由见 §1 的表下第 2 条）。
> 另外提醒：你现在给的这对凭据是**小程序**的，**App 端微信登录用不了这一对**（见 §5）。

## 0. 小程序有两个 IP 白名单，别配错（2026-09-29 按官方文档校正）

官方文档：<https://developers.weixin.qq.com/doc/oplatform/developers/basic_func/ip_whitelist>（平台基础功能 → API IP 白名单）

| 官方名 | 操作路径 | 管什么 | 与本项目的关系 |
|---|---|---|---|
| **API IP 白名单** | 开发管理 → 开发设置 → **开发者 ID** → IP 白名单 | 开启后只有名单内 IP 才能调用**参数为 `AppSecret` 的接口**（`access_token`、`stable_token`、重置调用次数等） | **登录要加白的就是这一条**。`sns/jscode2session` 参数含 `secret` ⇒ 归它管，不在名单内报 `40164` |
| **代码上传 IP 白名单** | 开发管理 → 开发设置 → **小程序代码上传** → IP 白名单 | 只有名单内 IP 才能调「代码上传接口」，即影响 `miniprogram-ci` | **与本项目无关**。我们用开发者工具的登录态上传，不需要它，配错了也不会影响登录 |

两者共同规则：每个小程序最多 **10** 个；支持具体 IP 与 IP 段（`1.2.3.4` / `1.2.3.*` / `1.2.3.0/24`）；**不支持「IP:端口」**；要填**出口公网 IP**（服务器上 `curl ifconfig.me` 查），不是内网 IP。

> 与「服务器域名」的关系：那是**另一套体系**（管 `wx.request` 等小程序→后端的网络通信），和 `40164` 没有任何关系。三者在后台是三个独立入口。

## 1. 线上实测（2026-09-25，只读探针）

用 `node scripts/check-wechat-login.js` 复现：

| # | 探针 | 结果 | 结论 |
|---|---|---|---|
| 1 | 直连微信 `jscode2session`（**本机** IP + 你的 AppID/Secret + 假 code） | `{"errcode":40164,"errmsg":"invalid ip 112.0.140.70 ipv6 ::ffff:112.0.140.70, not in whitelist"}` | **API IP 白名单拦截**。微信先查 IP 再查 Secret，所以这一条**不能证明 Secret 对不对** |
| 1b | 同上，但把 AppID 改成一个假的 | `{"errcode":40013,"errmsg":"invalid appid"}` | 反证：**你的 AppID `wx976f673896c8b565` 有效**（错 AppID 会先报 40013） |
| 2 | `POST /api/v1/sessions/wechat`，空 body `{}` | `400 VALIDATION_FAILED — expected string, received undefined` | **后端是公开路由且做参数校验** ✅（登录接口本该无需鉴权） |
| 3 | 同上，body `{"code":"<假 code>"}` | `401 UNAUTHORIZED — 登录凭证已失效，请重试` | **后端 code2Session 代理已实现** ✅：假 code 被拒绝。但**分辨不出拒绝原因**（见下第 2 条） |

> ⚠️ 由此更正一条旧判断：此前记录的「`/api/v1/sessions/wechat` 返回 401 = 接口在但没配 AppID/Secret」是**错的**。
> 401 是**假 code 被微信拒绝后的正常映射**；`{}` 返回 400 而不是 401，说明路由没有被鉴权中间件挡住。

**关于第 1 条，有两点必须说清（2026-09-29 校正，此前表述有误）**：

1. `errmsg` 里的那个 IP（`112.0.140.70`）是**跑探针这台机器的出口公网 IP**，**不是后端服务器的 IP**。
   探针是在本机跑的，微信看到的就是本机地址。
2. 因此这条实测**只能**得出两个结论：① 该白名单**已开启**（按官方文档，`40164` 只在白名单开启后出现）；
   ② **本机**不在名单内。**它完全不能说明后端服务器在不在名单内** —— 第 3 条把「code 无效」和
   「后端出口 IP 未白名单」压成了同一个 401，探针从响应上分辨不出来。

**所以下一步不是直接加白，而是先确认**（顺序很重要）：

| 步骤 | 做什么 | 判据 |
|---|---|---|
| 1 | 打开**开发者 ID → IP 白名单**，**看名单里现在有什么** | 若里面已有后端服务器出口 IP ⇒ 说明 40164 不是真机登录失败的原因，别再往这个方向修 |
| 2 | 在后端服务器上 `curl ifconfig.me` 拿出口公网 IP，和名单比对 | 不在名单里 ⇒ 加进去；顺带把**本机**出口 IP 也加上，探针才能自证 |
| 3 | 后端把微信原始 `errcode/errmsg` 打进日志 | `errmsg` 里**就带着后端自己的出口 IP**，不必登服务器也能知道该加哪个 |

加白后，`node scripts/check-wechat-login.js` 的 [1/3] 会从 `BLOCKED` 变成 `40029 invalid code` ——
那才是「AppID / AppSecret / 白名单三者全对」的完整证明。

### 1.1 另外两项只能在微信公众平台手动配（探针查不到，2026-09-28 补记）

| # | 位置 | 必须满足 | 漏了会怎样 |
|---|---|---|---|
| A | 开发管理 → 开发设置 → **服务器域名** → `request` 合法域名 | 含 `api.sankengcloset.icu` | 小程序端**连请求都发不出去**。真机报「不在以下 request 合法域名列表中」；而开发者工具勾了「不校验合法域名」时会**假装正常**，所以必须在**真机**上验一次，不能只看工具 |
| B | 同上，域名本身 | HTTPS + 已 **ICP 备案** | 微信硬性要求，未备案域名加不进去 |

A（服务器域名）和 **API IP 白名单**是**两个方向**的墙，别混：API IP 白名单管「**后端服务器 → 微信**」这一跳
（在**开发者 ID** 下）；服务器域名管「**小程序 → 后端**」这一跳。两边都通，登录才真正跑得起来。
（第三个容易混的是「**小程序代码上传 → IP 白名单**」，它只管 `miniprogram-ci` 上传代码，与登录无关，见 §0。）

### 1.2 复诊（2026-09-29）：白名单已核对无误，401 **不是** 40164

真机上微信登录稳定失败，`POST /api/v1/sessions/wechat` → `401 Unauthorized`。复诊结论：

**① 白名单这一条已经排除。** 现场两处证据完全一致：

| 来源 | 值 |
|---|---|
| 服务器上 `curl ifconfig.me` | `8.133.168.216` |
| 公众平台「开发者 ID → IP 白名单」 | `8.133.168.216` |

⇒ 「后端出口 IP 不在白名单」不成立，这条线到此为止，**不要再往这里改配置**。

> ⚠️ 教训：`scripts/check-wechat-login.js` 的 [1/3] 是**本机**发出的请求，`errmsg` 里那个 IP
> （当时是 `112.0.140.70`）是**本机出口 IP**，不是后端 IP。它只能证明「白名单已开启」+「本机不在名单内」，
> **证明不了后端在不在名单内**。此前据它下过「后端没加白」的结论，是错的。

**② 剩下的嫌疑只有两类。**

| # | 嫌疑 | 说明 |
|---|---|---|
| 1 | 微信 errcode | `40013 invalid appid`（AppID 不符）/ `40125 invalid appsecret`（Secret 错或已重置）/ `40029 invalid code`（code 无效或**已被用过**） |
| 2 | **后端 catch 太宽**（嫌疑最大） | 后端把**所有** code2Session 失败压成同一句 `401 / 登录凭证已失效，请重试`。如果 code2Session 其实成功了、之后**建号/查库**抛了错，也会被同一句 401 吞掉，前端完全看不出来 |

**③ 决定性一步（必须在服务器上跑，因为只有它的 IP 在白名单里）：**

```bash
curl -s "https://api.weixin.qq.com/sns/jscode2session?appid=wx976f673896c8b565&secret=$WECHAT_MP_APPSECRET&js_code=test&grant_type=authorization_code"
```

| 返回 | 含义 |
|---|---|
| `40029 invalid code` | AppID + AppSecret + IP **全部正确** ⇒ 病因在「code 本身」或后端代码里（对应嫌疑 2） |
| `40013 invalid appid` | 后端 env 的 AppID 与小程序不是同一个 |
| `40125 invalid appsecret` | 后端 env 的 AppSecret 错 / 已重置 |
| `40164 not in whitelist` | **调微信的机器不止一台**（多 origin / 换过机器），每台的出口 IP 都要进白名单 |

**④ 本地已能排除的（不用再查）：**

- AppID 三处一致：`config/wechat.uts` / `manifest.json` / 产物 `project.config.json` 均为 `wx976f673896c8b565`
- `apiPost()` 是**单次** `uni.request`，**没有重试/重发**；`_state.loggingIn` 也挡住并发点击 ⇒「code 被消费两次」不成立
- 公开路由、参数校验正常：空 body → `400 VALIDATION_FAILED`，假 code → `401`（说明请求确实进到了 code2Session 分支）
- `access_token` 与本链路**无关**（见下文）；`api.sankengcloset.icu` 解析到 **4 个 IP（`223.111.27.109-112`）**，前面有 CDN/负载均衡 —— 若后端有多台 origin，白名单要**每台**都填

**⑤ requestId 已打通（这是唯一能停止「继续猜」的把手）。** 后端**每个**响应都带 `requestId`，
但原先 `parseResponse` 在 `throw` 之前只取了 `error.code`，**错误路径上把 requestId 丢了**。
现已全链路带上并在登录页显示「请求 ID req-xxx」：

```
api-client.uts  parseResponse：在 throw **之前**取出 requestId → ApiRequestError.requestId
                apiErrorRequestId(error)  ← 新增导出
session-store   _state.errorRequestId（与 errorMessage 必须成对清空，统一走 clearLoginError()）
pages/auth/login.uvue  错误卡里渲染「请求 ID {{ requestIdText }}」
```

有了它，用户只要把屏幕上的 `req-xxx` 报出来，后端就能直接捞到那一条日志、看到微信原始 `errcode/errmsg`。
回归测试 `tests/api-error-request-id.test.cjs`（用 vm 加载真实 `api-client.uts`、驱动真实 `parseResponse`）。

**⑥ 追加（2026-09-29 12:25）：服务器上出现了 `41004 appsecret missing`。**

```json
{"errcode":41004,"errmsg":"appsecret missing, rid: 6abafe4f-3dc02598-7733466e"}
```

**这个错误的字面含义是「请求里没有可用的 `secret` 参数」，不是「Secret 值不对」**（值不对是 `40125`）。
所以看到它**不要去公众平台重置 AppSecret**，那是白费。两个成因：

| # | 成因 | 怎么查 |
|---|---|---|
| 1 | **参数名写错**。微信只认 `secret`，写成 `appsecret` / `app_secret` / `appSecret` 都报这条 | 看后端拼 URL 的那一行 |
| 2 | **变量是空的**：env 没加载 / 名字拼错 / **改了 `.env` 却没重启进程**（跑着的老进程还是旧 env） | 见下方命令 |

> ⚠️ **手工 curl 的假象**：写成 `secret=$SOMETHING` 时，变量不存在会被 shell 展开成**空串**，
> 于是「你什么都没传」会被误读成「后端配错了」。本项目真实变量名是
> **`WECHAT_MP_APP_SECRET`**（见 `.env.local` 与 §3.1），不是 `SECRET`。

**实测到的检查顺序（2026-09-29，本机复现）：微信先查 IP 白名单，后查参数。**

| 发出请求的机器 | 带空 `secret` 的结果 |
|---|---|
| 本机（**不在**白名单） | `40164 not in whitelist` |
| 服务器（**已**白名单） | `41004 appsecret missing` |

⇒ 「能收到 `41004`」本身就是**白名单已通过的二次证明**（只有在白名单内的机器上，参数校验才轮得到）。
同时也说明那次请求**确实没带上可用的 secret** —— 但它究竟是被 shell 展开成空串，
还是后端自己没传，这一条命令区分不了，必须用后端**进程里**的真值再跑一次。

**修正后的服务器自检（不依赖 Docker、不手敲变量名）：**

> 先给个指纹：`curl -sI https://api.sankengcloset.icu` 的响应头是
> `server: ESA` + `via: 1.1 Caddy, ens-cache23.cn4502[…]` + `set-cookie: acw_tc=…`
> ⇒ **阿里云 ESA(CDN/WAF) → Caddy 源站**，源站是自建的一台机器，不是微信云托管。

**0) 先确认 docker 到底有没有** —— 本仓库 runbook 写明生产库跑在 `sankeng-pg_postgres_1` 容器里，
所以「没有 docker」更可能是**权限或 PATH** 问题，不是真没有：

```bash
command -v docker || ls -l /usr/bin/docker /usr/local/bin/docker 2>/dev/null || echo "PATH 里确实没有"
sudo docker ps --format '{{.Names}}\t{{.Image}}' 2>&1 | head -10   # ← docker.sock 默认只有 root 能读写
```

**1) 找 API 进程 / 监听端口（不管有没有 docker 都能用）**

```bash
ps -ef | grep -viE 'grep' | grep -iE 'caddy|node|deno|bun|pm2|python' | head -20
sudo ss -lntp | head -20
```

**2) 取后端**进程**的 env 真值**（只报长度，绝不打印值）

```bash
PID=$(pgrep -f 'node|caddy' | head -1); echo "PID=$PID"
sudo tr '\0' '\n' < /proc/$PID/environ | grep -E '^WECHAT_' | while IFS='=' read -r k v; do echo "$k  len=${#v}"; done
```

> 如果进程 env 里**没有** `WECHAT_*`（后端用 dotenv 从文件读，`/proc/*/environ` 是看不到的），
> 改查部署目录里的 `.env`：`sudo awk -F= '/^WECHAT_/{print $1" len="length($2)}' ./.env`
> 最要紧的是**别手敲变量名**，变量不存在会被 shell 展开成空串，伪造出一个假的 41004。

**3) 直接发一次 code2Session（写成文件跑，避免引号地狱）**

```bash
cd <后端部署目录>            # 里面应有 .env；没有就删掉下面读 .env 的兜底
cat > /tmp/wxcheck.js <<'JS'
const fs = require('fs')
let fileEnv = {}
if (fs.existsSync('.env')) {
  for (const line of fs.readFileSync('.env', 'utf8').split(/\r?\n/)) {
    const m = /^\s*([A-Za-z0-9_]+)\s*=\s*(.*)$/.exec(line)
    if (m) fileEnv[m[1]] = m[2].trim().replace(/^["']|["']$/g, '')
  }
}
const env = { ...fileEnv, ...process.env }
// ⚠️ 变量名必须取**后端代码实际读的那个**（2026-09-29 实测：后端读的是 WECHAT_APP_ID /
//    WECHAT_APP_SECRET，不是本仓库 .env.local 里的 WECHAT_MP_APPID / WECHAT_MP_APP_SECRET）。
//    写死名字会取到空串 ⇒ 直接伪造出一个假的 41004。这里两种都试并打印命中哪一组。
const pick = (...names) => {
  for (const n of names) if (env[n]) return { name: n, value: env[n] }
  return { name: '(全部为空)', value: '' }
}
const a = pick('WECHAT_APP_ID', 'WECHAT_MP_APPID')
const s = pick('WECHAT_APP_SECRET', 'WECHAT_MP_APP_SECRET')
console.log('APPID  取自 ' + a.name + '  len=' + a.value.length)
console.log('SECRET 取自 ' + s.name + '  len=' + s.value.length)
fetch('https://api.weixin.qq.com/sns/jscode2session?appid=' + a.value + '&secret=' + s.value
  + '&js_code=test&grant_type=authorization_code')
  .then(r => r.text()).then(t => console.log(t))
JS
node /tmp/wxcheck.js
```

（若 API 在 docker 里：`docker cp /tmp/wxcheck.js <容器>:/tmp/ && docker exec <容器> node /tmp/wxcheck.js`；
容器里没有 node 就 `docker exec <容器> printenv | grep -E '^WECHAT_' | sed -E 's/=.{4,}/=<非空>/'` 只判断是否存在。）

| 第 3 步返回 | 结论 |
|---|---|
| `41004 appsecret missing` | **找到病因**：后端没传 secret（参数名写成 `appsecret`，或 env 是空的 / 改了 `.env` 没重启进程）⇒ 修 env 并**重启进程** |
| `40029 invalid code` | 凭据 + IP 全对 ⇒ 问题在 code 或 code2Session **之后**的代码（对应 ②） |
| `40125 invalid appsecret` | Secret 值错 / 已重置（重新生成，同步 env，重启） |
| `40164 not in whitelist` | 这台不是真正调微信的机器 ⇒ 白名单按机器补；**同时说明 ① 的结论要撤回** |

> ⚠️ **前提校验**：`8.133.168.216` 进白名单，只能证明**那台 ECS 能调微信**。
> 「40164 已排除」成立的前提是 **API 就跑在那台机器上** —— 第 1 步能确认（`sudo ss -lntp` 里
> 80/443 是 Caddy，Caddy 的 `reverse_proxy` 指向本机 API 端口）。若 API 其实在别处，
> 那次 41004 与登录无关，白名单结论必须重来。

**⑦ 结论（2026-09-29 22:5x）：原始 errcode = `40125 invalid appsecret`。**

服务器用**被测进程自己的 env**（PM2 `sankengcloset-api` → `start-prod.sh` → `node dist/src/server.js`，
PID 1930，监听 `0.0.0.0:8787`）直连 code2Session，拿到：

```json
{"errcode":40125,"errmsg":"invalid appsecret"}
```

已排除项，全部有证据：

| 项 | 证据 |
|---|---|
| 白名单（`40164`） | 回的是 `40125` 而非 `40164`；Caddy `reverse_proxy → dial 127.0.0.1:8787`，出口 IP `8.133.168.216`，API 确实跑在白名单那台机器上 |
| 空 secret（`41004`） | `/proc/1930/environ` 里 `WECHAT_APP_SECRET` len=32，md5 与 `.env.production` 一致 ⇒ 非空，且确实是文件里那个值 |
| 改了 `.env` 没重启进程 | 同上（进程 env 与文件一致，进程 09-20 重启过） |
| 参数名写错（`appsecret` vs `secret`） | `wechat-auth.ts` 用的是 `appid/secret/js_code/grant_type` |

⇒ 凭据、IP、参数名全对，**只剩 secret 值本身被微信拒绝**。两种可能：
① 该值已被重置（旧值立即失效）；② **appid 与 secret 不配对**（拿了另一个应用的 secret）。

**重置前再做一次零成本交叉验证**（只比 md5，不暴露任何明文）：

```bash
# appid 侧：期望 14504ba0f1908f393575c2d9b11a7c80（= wx976f673896c8b565）
printf '%s' "$WECHAT_APP_ID" | md5sum
# secret 侧：期望 821be8b956fa42963b2ec25bb103119b（= 本仓库 .env.local 里 2026-09-25 记录的值）
printf '%s' "$WECHAT_APP_SECRET" | md5sum
```

| appid md5 | secret md5 | 结论 |
|---|---|---|
| 相符 | 相符 | 服务器用的就是我们记录的那个值 ⇒ 该值确实已失效（被重置，或从未配对）⇒ **重置 AppSecret** |
| 不符 | 任意 | **不是 secret 的问题**，是 appid 指错了应用 ⇒ 改 appid 即可，**别去重置 secret** |
| 相符 | 不符 | 有人往 `.env.production` 写了别的值（大概率是另一个应用的 secret）⇒ 换成正确值 |

**关于 `req-1Iz`**：后端 09-20 至今 2100 个 reqId 全是 base36 小写、无大写 `I`；
最接近的是 **`req-1lz`**（`POST /api/v1/sessions/wechat → 401`，时间对得上）⇒ `I`/`l` 字形混淆，就是同一次失败。

**但 requestId 这条路本来就捞不到病因**：`wechat-auth.ts` 在任何 errcode 上都直接
`throw AppProblem(401, 'UNAUTHORIZED', '登录凭证已失效')`，微信的原始 errcode **从未进日志**。
所以这次的结论是**直连实测**拿到的，不是 grep 日志 —— 这正是 §3.2.1 要改的那一处。

## 2. 链路

```
小程序端                       后端 api.sankengcloset.icu              微信
wx.login()  ──code(5min)──▶  POST /api/v1/sessions/wechat
                              code2Session(appid, secret, code)  ──▶  jscode2session
                                                              ◀──  openid / unionid / session_key
                              upsert user(openid) → 签发 accessToken/refreshToken
         ◀── { accessToken, refreshToken, userId }  ────
GET /api/v1/me (Bearer) ──▶   返回昵称/头像 → 落本地会话
```

**AppSecret 只出现在「后端 → 微信」这一跳**，永远不经过客户端。

### 3.1.1 要的是**哪一个** secret（2026-09-29 易错点）

一个主体下往往有好几个「密钥」，只有**一个**对得上这次调用，别拿错：

| 密钥 | 出处 | 管什么 | 这次要吗 |
|---|---|---|---|
| **小程序 AppSecret（小程序密钥）** | 公众平台 → 开发管理 → 开发设置 → **开发者 ID** → 「AppSecret(小程序密钥)」 | `sns/jscode2session` 的 `secret` | ✅ **要的就是它** |
| 公众号 AppSecret | 公众平台（公众号）→ 设置与开发 → 基本配置 | 网页授权 `sns/oauth2/access_token` | ❌ |
| 开放平台 · 移动应用 AppSecret | open.weixin.qq.com → 管理中心 → 移动应用 | App 端微信登录（即 `config/wechat.uts` 里 `WECHAT_APP_LOGIN_CONFIGURED` 那套，**另一套凭据**） | ❌ 另算 |
| 微信支付 APIv3 密钥 / API 密钥 | 商户平台 | 支付签名 | ❌ |
| 小程序代码上传密钥 | 公众平台 → 开发管理 → 小程序代码上传 | miniprogram-ci 上传代码 | ❌ |
| `access_token` | 接口换取 | — | ❌ 与登录链路无关（见 §1.2） |

判定依据（不是猜的，三条独立证据）：

1. 失败发生在 `https://api.weixin.qq.com/sns/jscode2session` —— 这是**小程序（含小游戏）登录凭证校验**接口，
   它的 `secret` 参数按定义只能填**该小程序的 AppSecret**（公众号走 `sns/oauth2/access_token`，是另一个接口）；
2. 后端发出的 appid 是 len=18、`wx9` 开头，与本仓库 `config/wechat.uts` 的 `wx976f673896c8b565` 一致
   （本仓库 `.env.local` 的 `WECHAT_MP_APPID` md5 = `14504ba0f1908f393575c2d9b11a7c80`，与 `wx976f673896c8b565` 一致，已本地核对）；
3. ⚠️ **AppSecret 必须与这个 AppID 出自同一个小程序**。同一主体下的**另一个**小程序、或该主体的**公众号**
   的 AppSecret，填上去只会继续得到 `40125` —— 这正是 §1.2 ⑦ 里「appid 与 secret 不配对」那一支。

> 路径速记：`mp.weixin.qq.com` → 登录（**管理员微信扫码**）→ 左侧「开发管理」→「开发设置」→
> 页面上方「开发者 ID」区块里，AppID 下面一行就是 AppSecret，右侧「重置」。
> 重置后**只显示一次**，当场复制；重置会**立即作废旧值**，确认没有别的服务在用同一个 secret。

### 3.1.2 换 AppSecret 的落地步骤（2026-09-29）

> **已经比过 md5 了**：服务器 `.env.production` 里那份（md5 `821be8b956fa42963b2ec25bb103119b`，
> 与本仓库 `.env.local` 同一个值）**就是被微信回 `40125` 的那个值**；后台取到的新值
> （md5 `6e6683ffd5b0847b58f6228c9aadf370`）与它**不是同一个串**
> ⇒ **不需要重置 AppSecret，直接替换即可**（重置反而会作废别处在用的凭据）。

**推荐：用本仓库带的脚本，一条命令做完全部五个动作** —— `scripts/server/apply-wechat-appsecret.sh`：

```bash

```

它会依次完成：备份 → **交互式读入新值**（`read -rsp`，不回显、不进 shell 历史、不进 `ps`）→
**只替换 `WECHAT_APP_SECRET` 那一行**（其余行逐字节保留；用 awk 显式 print，避免 `FS/OFS` 重排
把 `DATABASE_URL=...?a=1&b=2` 这类含 `=` 的值改坏）→ 落盘校验 len/md5（不符就**中止且不重启**）→
`pm2 restart --update-env` → **核对运行中进程的 `/proc/<pid>/environ`**（文件对了但进程还是旧 env 才是真坑）。

本机已用 fixture 实测：其他行逐字节未变、md5 得到 `6e6683ff…`、行数守卫与失败中止都生效。

下面是手工等价步骤（不想用脚本时照做）：

1. **在服务器上手工编辑**。不要 `echo '...' >> .env`、不要把值放进任何命令行参数
   （会进 shell 历史与 `ps` 输出）：

   ```
   vi /home/admin/projects/sankengcloset_service/.env.production
   ```

   只改 `WECHAT_APP_SECRET=` 这一行。**不要加引号、不要留尾空格。**
2. **落盘校验（不打印明文）**：

   ```bash
   cd /home/admin/projects/sankengcloset_service
   awk -F= '/^WECHAT_APP_SECRET=/{print "len="length($2)}' .env.production           # 期望 len=32
   awk -F= '/^WECHAT_APP_SECRET=/{print $2}' .env.production | tr -d '\n' | md5sum   # 期望 6e6683ffd5b0847b58f6228c9aadf370
   ```

   len=32 但 md5 不符 ⇒ 多半带了引号或空格（md5 是对**裸值**算的，顺手也能验出引号问题）。
3. 与 §3.2.1 的三档分流改动**合并成一次**构建与重启：
   `npm run build` → `pm2 restart sankengcloset-api --update-env`。
4. **服务器侧验证**：`node /tmp/wxcheck.js` → 期望 `40029 invalid code`。
5. **远程验证（没有白名单的机器也能做）**：三档分流落地后错误码才可区分 ——

   ```bash
   curl -s -X POST https://api.sankengcloset.icu/api/v1/sessions/wechat \
     -H 'content-type: application/json' -d '{"code":"test"}'
   ```

   | 返回 | 含义 |
   |---|---|
   | `503` + `WECHAT_CREDENTIAL_INVALID` | 凭据仍被拒 ⇒ secret 还是不对 |
   | `503` + `WECHAT_IP_NOT_WHITELIST` | 调用方不在白名单（意外，白名单已核对过） |
   | `401` + `UNAUTHORIZED` | ✅ **凭据已被接受** —— 假 code 本来就该报这个 ⇒ 修好了 |

   ⚠️ 第 5 步的前提是**第 3 步的分流已经上线**；否则所有 code2Session 失败都塌成同一个 `401`，
   这一步分辨不出「凭据错」与「code 错」。

   本仓库探针已内建这条判断，但**默认不会**把「收到 401」当成凭据通过（那会是个假阳性）：


### 3.2 接口

`POST /api/v1/sessions/wechat` — **必须公开**（不能挂鉴权中间件）

请求：

```json
{ "code": "wx.login 返回的 code（5 分钟有效、一次性）", "deviceId": "可选" }
```

> `deviceId` 真的可以不给。小程序端这个字段已被微信**废弃**，个别基础库/PC 端返回 `undefined`；
> 早期客户端把这个 `undefined` 塞进请求体变成 `"deviceId": null`，后端 zod 判它
> 「expected string」⇒ **配置全对也会被 400 掉**。现在客户端已改为：拿不到就**不带这个键**。
> 后端 schema 请保持 `deviceId` 为**可选**（缺键必须通过校验），不要写成 `string` 必填。

成功 `200`：

```json
{
  "requestId": "req_01H...",
  "data": { "accessToken": "...", "refreshToken": "...", "userId": "usr_xxx" }
}
```

失败映射（客户端 `wechatLoginErrorMessage()` 已按此分流）：

| 场景 | 建议状态码 | `error.code` | 客户端提示 |
|---|---|---|---|
| 缺 `code` / 类型不对 | `400` | `VALIDATION_FAILED` | 「微信登录参数有误，请更新到最新版本后重试」 |
| code 无效 / 已用过 / 已过期（微信 `40029`/`40163`） | `401` | `UNAUTHORIZED` | 「微信授权已失效，请重新点击登录」 |
| **微信侧 `40164`（IP 未白名单）** | `503` | `WECHAT_IP_NOT_WHITELIST` | 「登录服务未配置好：服务器 IP 不在微信白名单，请联系管理员」 |
| **微信侧凭据被拒（`40125`/`40013`/`41002`/`41004`/`41008`）** | `503` | `WECHAT_CREDENTIAL_INVALID` | 「登录服务未配置好：服务器微信凭据无效，请联系管理员」 |
| 微信侧 `-1`（系统繁忙） | `503` | `SERVER_ERROR` | 「登录服务暂时不可用，请稍后重试」 |
| 路由不存在 | `404` | `NOT_FOUND` | 「微信登录服务尚未上线，请稍后再试」 |

### 3.2.1 `error.code` 是硬要求，不是可选项（2026-09-28 补记）

线上现状：后端**已经**在错误体里带 `error.code`（实测 `{"error":{"code":"VALIDATION_FAILED","message":"...","retryable":false}}`），
客户端 `stores/session-store.uts` 现已读取它（`apiErrorCode()`）并优先按 code 分流。

**必须补的一处**：`40164` 现在被后端一起映射成了 `401 UNAUTHORIZED — 登录凭证已失效，请重试`。
这会导致两个病因完全不同的故障显示出**同一句话**：

- code 过期 → 用户再点一次就好；
- IP 未白名单 → 用户点一万次也没用，必须管理员改配置。

排查时就被这句话绕过一圈（见 §1）。**2026-09-29 实测表明「其余错误照旧 401」这条建议也是错的**：
真实拿到的原始 errcode 是 `40125`，它属于「服务端凭据被拒」，用户重试一万次也不会好，
却被压成 `401 登录凭证已失效，请重试`，与「code 过期」完全同文案 ⇒ 又一个死循环。

请在 API 仓库（`burnkings/sankengcloset-api`）的 `wechat-auth.ts` 里，**在抛错之前**改成三档分流：

```ts
// 1) 原始 errcode 必须先落日志 —— 否则拿到 reqId 也捞不到病因（§1.2 ⑦ 就是这么被绕过的）
request.log.warn({ errcode: payload.errcode, errmsg: payload.errmsg })

switch (payload.errcode) {
  case 40164:                            // IP 不在白名单 —— 管理员改配置
    throw new AppProblem(503, 'WECHAT_IP_NOT_WHITELIST', '服务器 IP 不在微信白名单')
  case 40013:                            // AppID 不符
  case 40125:                            // AppSecret 值无效
  case 41002: case 41004: case 41008:    // 参数没传到位（键名错 / 值为空）
    throw new AppProblem(503, 'WECHAT_CREDENTIAL_INVALID', '微信凭据无效')
  default:                               // 40029 / 40163 code 无效或已用过、-1 系统繁忙 …
    throw new AppProblem(401, 'UNAUTHORIZED', '登录凭证已失效，请重试')
}
```

⚠️ **三档必须分开，客户端文案完全依赖 `error.code`**：

- `WECHAT_IP_NOT_WHITELIST` / `WECHAT_CREDENTIAL_INVALID` 都收敛到「登录服务未配置好…请联系管理员」；
- 若把凭据类也丢进 `503` 却不给 code，客户端会落到 503 那档的「请稍后重试」—— **依然死循环**。
  客户端这两道闸已经加好（`stores/session-store.uts` 的 `wechatLoginErrorMessage()` 前两支，
  `tests/wechat-login-error.test.cjs` §1 / §1.5 守着，含「不许出现『稍后重试』」断言），
  后端只要按上表的 code 透传即可。

**建议与换 secret 合并成一次重启**：改 `.env.production` + 改 `wechat-auth.ts` → `npm run build` →
`pm2 restart sankengcloset-api --update-env` → 再跑一次 `/tmp/wxcheck.js`：
**期望 `40029 invalid code`**（`js_code=test` 本来就是假 code）。这一步同时证明
「凭据已生效」+「分流已生效」，一次重启拿到两个结论。

改完后 `node scripts/check-wechat-login.js` 的 [2/3] 段会打印 `error.code`，真机失败文案也会直接说清是哪一边的问题。

### 3.3 会话

## 5. App 端（Android / iOS）差异 —— 别复用小程序凭据

小程序登录和 App 微信登录是**两套完全独立的凭据**：

| | 小程序端 | App 端 |
|---|---|---|
| 平台 | 微信公众平台（mp.weixin.qq.com） | **微信开放平台**（open.weixin.qq.com）· 移动应用 |
| AppID | `wx976f673896c8b565`（已配） | **另一个** AppID，需先创建「移动应用」并通过审核 |
| 额外要求 | 无 | 登记**包名 + 应用签名**（与 `manifest.json` 的 `appid`、`release.keystore` 指纹一致） |
| 客户端调用 | `wx.login()` 拿 code | `uni.login({provider:'weixin'})`，需在 `manifest.json` 配 `app-plus.distribute.sdkConfigs.oauth.weixin` |

在小程序 AppID/Secret 上做 App 端登录**一定失败**。所以：

- 现在给的是小程序凭据 → **小程序端可以立刻跑通**（白名单加完即可）；
- App 端要另开开放平台移动应用，审核通过后把 `config/wechat.uts` 的 `WECHAT_APP_LOGIN_CONFIGURED` 改为 `true`，
  并在 `manifest.json` 里补 SDK 配置。

## 7. 安全红线

1. **AppSecret 绝不进客户端**（小程序包 / APK 都能被反编译提取，微信明令禁止并会处罚）；
2. 前端仓库只放 AppID（`config/wechat.uts`），Secret 只放 `.env.local` / 服务器环境变量；
3. `session_key` 不下发；日志里不打印 `secret`、`accessToken`、`openid` 全量；
4. `code` 一次性、5 分钟过期 —— 后端换到 `openid` 后即失效，重试必须重新 `wx.login`。
5. **不要把 AppSecret 贴进聊天 / issue / 工单 / 截图**（2026-09-29 实际发生过一次）。
   一旦贴出就视为**已泄露**：聊天记录、截图、模型上下文都留痕。
   正确的传递方式只有一种 —— **在目标机器的编辑器里直接键入**（服务器 `vi .env.production`），
   需要核验就用 §3.1.2 的 md5 命令：**只比哈希，不搬明文**。
   若已经贴出，建议在本轮验证通过后**再重置一次**，新值只写进服务器 env，不再经过任何对话。
6. 排查过程里禁止用「占位变量名」发请求（`secret=$SECRET`）—— 变量不存在会展开成空串，
   会伪造出一个假的 `41004`，把结论带偏（本项目踩过两次，见 §1.2 ⑥）。
