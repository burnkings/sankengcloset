# 屏幕识别点击方案：可行性评估（2026-09-23）

问题：能否用「截屏 + 视觉识别 + 模拟点击」替代淘宝桌面版 MCP，绕开自动化风控？

---

## 一、本机能力实测（已验证）

| 能力 | 状态 | 实测结果 |
|---|---|---|
| 枚举窗口 / 取 rect | 可用 | 淘宝窗口 hwnd=6687568，rect=(621,228,2334,1311)，1713×1083 |
| 屏幕区域截图 | 可用 | `ImageGrab.grab(bbox, all_screens=True)` 成功，9611 色 |
| 后台截图（不需前台） | 可用 | `PrintWindow(hwnd, hdc, 0x2)` 返回 1，图正常无黑屏 |
| 模拟输入 | 可用 | `user32.SendInput` 存在，`GetCursorPos` 正常 |
| 屏幕分辨率 | 2560×1600，DPI 感知已开 | `SetProcessDPIAware()` 生效 |
| **中文 OCR** | 可用 | RapidOCR：截图 **0.09-0.19s**，初始化 0.33s，推理 **1.8-2.2s**，29-41 文字块 |
| **文字定位精度** | 可用 | 输出屏幕绝对坐标，实测「请登录」→(2077,271)、「购物车」→(745,536)、「提交」→(1577,1196) |

完整链路验证脚本：`scripts/gui-automation/ocr-test.py`（截屏 → OCR → 文字+坐标）。

**结论：技术链路完整可行，无环境级阻碍。**

## 一之二、但实测发现问题：淘宝正在风控拦截

OCR 识别结果直接读到淘宝窗口当前状态：

```
[0.81] (1577, 344)  验证码拦截
[0.74] (2077, 271)  请登录
[0.54] (1577,1196)  提交
```

截图确认为**滑块验证码拦截页**（带刷新图标 + 提交按钮 + 反馈码 `eb22bf886da439fcff856c652e4f2e34`），右上角同时显示「请登录」。

**这说明三件事：**

1. **风控已经被触发**。原因不是"用了 CLI 而不是模拟点击"，而是**固定节奏的高频访问**（每条约 20 秒、连续跑、批量导航）。换输入通道不会改变这个行为特征。
2. **登录态可能已失效**。需人工确认。
3. **继续跑采集只会加重拦截**。当前应先人工过验证码、恢复会话，再降低强度续跑。

这也解释了先前采集内容异常短（390 字符、无参数信息）——部分请求可能被拦在了验证页。

## 二、架构

```
① 窗口定位    EnumWindows 找淘宝 hwnd → GetWindowRect
              （窗口移动/缩放后需重新取 rect）
② 截屏        PrintWindow(0x2) 后台截图，或 ImageGrab 前台截屏
③ 识别        OCR（RapidOCR / PaddleOCR）拿文字 + bbox
              模板匹配（OpenCV matchTemplate）定位按钮图标
              两者结合：OCR 定锚点文字 → 相对偏移算按钮坐标
④ 点击        SendInput 硬件级输入
              · 贝塞尔曲线移动（20-40 个中间点）+ 随机抖动
              · 落点在目标框内随机（不点中心）
              · 随机按下时长 60-160ms
⑤ 闭环确认    点击后再截屏 OCR，确认状态变化；未变则重试或跳过
```

反检测要点：随机化延迟、鼠标轨迹、落点、按键时长；避免固定节奏。

## 三、关键判断

### 能绕开的
- **自动化框架指纹**：MCP/CLI 走 Electron 调试通道，客户端侧理论上可检测调用来源。SendInput 走 Windows 输入栈，产生的是真实硬件级输入事件，无自动化标记。

### 绕不开的
- **行为风控**。淘宝风控的主体是行为模型：访问频率、浏览-点击时序、账号历史、设备指纹、IP。输入通道换了，行为特征还在。同样是 20 秒一次机械操作，照样会被限。
- 想真正降低命中率，要做的是**改变行为分布**，不是改变输入通道。

### 代价（和 CLI 对比）

| 维度 | CLI（当前） | 屏幕识别点击 |
|---|---|---|
| 单条耗时 | 16-20 秒 | 每步截图+OCR 1-3 秒，一条商品 5-7 步 → **40-120 秒** |
| 3247 条预估 | 10-18 小时 | **数天** |
| 前台要求 | 无，可后台跑 | **窗口必须可见且在前台**，不能锁屏、不能切窗口 |
| 稳定性 | DOM 稳定 | 分辨率/缩放/主题/页面改版全部会失效 |
| 误操作风险 | 无（只读接口） | **有**：定位偏差可能点到「加入购物车」「立即购买」「提交订单」 |
| 开发成本 | 已完成 | 需重新实现识别/定位/重试/异常恢复 |

**最致命的两条**：
1. 「窗口必须前台」直接否掉了"不用守着电脑"的诉求——你一动鼠标、一切窗口就乱。
2. 误点购买类按钮的后果不可逆。只读需求引入写操作风险，不划算。

## 四、建议

### 优先做：给现有 CLI 加人类化随机（成本低、收益直接）

当前 `fetch.ps1` 是固定 `-Delay 6`，这是最容易被识别的特征。改成：

| 项 | 现在 | 改成 |
|---|---|---|
| 条间延迟 | 固定 6s | **4-11 秒随机** |
| 导航后等待 | 固定 5s | 4-7 秒随机 |
| 批间休息 | 每 25 条停 60s | 每 15-30 条（随机）停 45-180 秒（随机） |
| 滚动行为 | 固定 600/1200 | 随机次数、随机幅度，模拟浏览 |
| 连续时长 | 不限 | 跑 90-120 分钟停 20-40 分钟 |

这些改动小、见效直接，不引入新风险。

### 可选做：屏幕识别只用于「读」，不用于「点」

如果 CLI 确实拿不到某些内容，可以用截屏 + OCR 补读（例如懒加载区块、非结构化图文详情）。**不做模拟点击**，避免误触。

### 不建议：全量换成屏幕识别点击

代价（慢 5-10 倍 + 必须前台 + 误点风险）远超收益，且绕不过真正的风控逻辑。

## 五、顺带发现（需确认）

`PrintWindow` 截到的淘宝窗口当前显示的是**「淘宝桌面版MCP接口使用须知」授权页**，右上角显示**「请登录」**。

- 如果这是新弹出的授权确认页，可能需要**手动点击同意**才能继续使用 MCP 接口；
- 若登录态失效，采集会拿不到完整数据。

建议确认该页面是否已处理。
